# 批量打包上传提审 App Store 的技术方案

做 iOS 批量上架，最耗时间的不是写代码，而是重复操作。

一个 App 从准备到提审，至少要做这些事：

| 环节 | 主要操作 |
|---|---|
| 证书 | 证书、描述文件、Bundle ID、签名配置 |
| 创建 App | App Store Connect 创建 App、填写基础信息 |
| 打包上传 | Xcode 配置、Archive、Export、Upload |
| 内购 | 创建商品、截图、价格、审核信息 |
| 元数据 | 名称、描述、关键词、截图、隐私链接 |
| 提审 | 选择 Build、填写审核备注、提交审核 |
| 状态跟踪 | 查询审核状态、记录失败原因 |

如果一周只发 1 个 App，人工还能接受。

如果一周要发 **30 到 50 个 App**，靠人工点后台，效率很低，也很容易漏步骤。

## 一、批量上架最容易卡在哪里

### 1. 账号和 App 太多

多个开发者账号、多个 App、多个 Bundle ID，人工切换很容易乱。

常见问题：

- 选错账号；
- 选错 App；
- Bundle ID 和本地工程不一致；
- 证书和描述文件不匹配；
- 上传到错误的 App 下面。

这类错误不难，但很浪费时间。

### 2. Xcode 打包链路太长

正常上传一个包，要经过：

1. 修改 Xcode 配置；
2. Archive；
3. Export IPA；
4. 上传 App Store Connect；
5. 等待处理；
6. 再回后台选择 Build。

一个包几十分钟不奇怪。

批量项目最怕的是中途失败，因为失败后还要翻日志、查签名、重新打包。

### 3. 内购配置重复

订阅、金币、会员、点数类 App，内购配置非常重复。

人工配置容易出错的地方：

| 项目 | 常见错误 |
|---|---|
| 商品 ID | 写错、重复、和代码不一致 |
| 价格 | 选错价格档位 |
| 截图 | 忘记上传或尺寸不对 |
| 审核说明 | 没写清楚入口 |
| 状态 | 商品没提交审核 |

内购错了，审核员找不到购买入口，很容易被 2.1(b) 卡住。

### 4. 审核状态不好跟踪

批量提审后，最麻烦的是状态跟踪。

几十个 App 同时跑，如果没有统一状态面板，很难知道：

- 哪个包上传完成；
- 哪个包还在处理 Build；
- 哪个包已经提审；
- 哪个包被拒；
- 哪个包需要补资料；
- 哪个账号当前任务失败。

## 二、我的自动化拆法

我把 App Store 批量上架拆成几个固定动作。

| 模块 | 作用 |
|---|---|
| 账号管理 | 维护多个 App Store Connect 账号 |
| App 管理 | 维护 App、Bundle ID、项目路径、配置 |
| 创建 App | 自动创建 App Store Connect 应用 |
| 上传程序 | 自动同步 Xcode 配置、构建、上传 |
| 上传内购 | 自动创建和提交内购信息 |
| 查询提审结果 | 读取审核状态和失败信息 |
| 完成提审 | Build 处理完成后自动提交审核 |
| 导出 Callback | 给外部系统同步任务状态 |
| 日志中心 | 记录每一步执行日志，方便排错 |

核心思路很简单：

**人工只负责准备配置，重复点击和等待交给工具。**

## 三、关键技术点

### 1. 账号和 App 配置标准化

批量上架第一步，是把账号、App、证书、工程路径做成结构化配置。

每个 App 至少要记录：

| 配置 | 说明 |
|---|---|
| 账号 | 使用哪个开发者账号 |
| App 名称 | App Store Connect 里的名称 |
| Bundle ID | 和 Xcode 工程一致 |
| 项目路径 | 本地 Xcode 工程位置 |
| Scheme | 打包使用的 Scheme |
| 证书状态 | 是否已准备完成 |
| 内购配置 | 是否需要上传内购 |

这一步做好，后面才能稳定批量执行。

### 2. 自动同步 Xcode 配置

批量项目不能每个都手工改 Xcode。

工具需要自动处理：

- Bundle Identifier；
- Display Name；
- Version / Build；
- Team；
- Provisioning Profile；
- Scheme；
- ExportOptions。

这些配置只要有一个错，就可能打包失败或者上传失败。

### 3. 自动打包上传

打包上传一般分三步：

| 步骤 | 说明 |
|---|---|
| Archive | 生成归档包 |
| Export | 导出 IPA |
| Upload | 上传到 App Store Connect |

自动化重点不是能不能跑命令，而是失败后能不能定位。

所以必须记录：

- 当前执行到哪一步；
- Xcode 原始日志；
- IPA 输出路径；
- 上传返回结果；
- App Store Connect 处理状态。

### 4. 自动处理内购

内购是批量上架里很适合自动化的部分。

可以自动处理：

- 创建内购商品；
- 上传商品截图；
- 设置价格；
- 填写审核说明；
- 提交内购审核；
- 查询内购状态。

这样可以减少商品 ID 写错、漏传截图、漏提审的问题。

### 5. 自动查询审核结果

提审后最需要的是状态同步。

工具要能查：

| 状态 | 用途 |
|---|---|
| Waiting for Review | 已进入等待审核 |
| In Review | 审核中 |
| Rejected | 被拒，等待处理 |
| Ready for Sale | 已上架 |
| Developer Action Needed | 需要开发者处理 |

批量项目一定要有任务中心和日志中心，否则后期排查会很痛苦。

## 五、实际效果

人工操作时，最大的问题是不可控。

同样一个流程，不同人操作，结果可能不一样。

自动化之后，收益主要在这几个点：

| 收益 | 说明 |
|---|---|
| 省时间 | 重复点击、等待、上传交给工具 |
| 少出错 | 账号、App、Bundle ID、Scheme 统一配置 |
| 好排查 | 每一步都有日志 |
| 可批量 | 多个 App 可以排队执行 |
| 状态清楚 | 哪个完成、哪个失败，一眼能看 |

对一周几十个 App 的团队来说，自动化不是锦上添花，是基础设施。

## 六、总结

批量打包上传提审 App Store，核心不是写一个上传脚本。

真正要解决的是完整链路：

1. 账号管理；
2. App 配置；
3. Xcode 打包；
4. IPA 上传；
5. 内购上传；
6. Build 处理；
7. 提交审核；
8. 状态查询；
9. 日志排错。
