近一年 iOS 马甲包，过审 500+ 个包。现在每周处理 **30 到 50 个 App**，机审 4.3 的几率低于 **3%**，给大家分享具体验证过的有效处理方案。
## 一、4.3 最常见的原因

| 原因 | 重点 |
|---|---|
| 二进制相似度高 | 代码、目录、字符串、Model、配置太像 |
| 元数据相似度高 | 名称、描述、关键词、截图文案太像 |
| 账号风控叠加 | 多次 4.3，或短时间大量提交同类包 |

我的经验是：**马甲包最核心的问题是二进制相似度，不是 UI。**

UI 一样、核心功能一样，不代表一定过不了。很多包图片素材不换，也可以过。真正容易出问题的是 IPA 里的工程特征太像。

## 二、二进制相似度主要看什么

二进制就是 IPA 安装包里的内容，包括代码、Framework、SDK、资源、配置文件、本地网页、AI 模型等。

同一个项目复制出来，如果不处理，类名、方法名、文件夹、字符串、Model、配置这些工程特征基本都一样。

所以只改包名、Logo、主题色，作用很有限。

## 三、元数据相似度主要看什么

元数据就是 App Store 页面上的内容，包括名称、副标题、描述、关键词、截图、预览视频、审核备注、隐私政策链接等。

元数据不用写复杂，重点是别像流水线批量生成。

## 四、怎么判断问题在哪

| 现象 | 优先判断 |
|---|---|
| 1 小时以内快速 4.3 | 机审、二进制、元数据、风控 |
| 同账号多个包连续快速 4.3 | 账号风控或批量特征 |
| 只有一个包 4.3 | 当前包自身相似度问题 |
| 等较久后 4.3 | 人审概率更高 |

机审更偏看二进制、元数据、SDK、私有 API、权限、账号风险。

人审更偏看功能是否完整、有没有违规点、数据源和展示内容是否重复、主题配色是否太模板。

过了机审后，人审通常简单很多。为了稳定率，我一般会顺手改主题配色和数据源。

## 五、被 4.3 后怎么救

我们救成功 4.3，常用两种方法。

### 方法一：换 5 图，写原创性回复

适合元数据相似、截图展示太模板、审核员认为产品重复的情况。

处理方式：

- 换一套 5 图；
- 截图文案重新写；
- App Review Notes 写清楚产品原创性、功能差异、内容来源；
- 重新提交审核。

### 方法二：换主题色、改功能、换资源重新提

适合人审后被 4.3，或者展示内容和其他包太像的情况。

处理方式：

- 换主题配色；
- 调整部分功能入口或展示方式；
- 换数据源；
- 换部分图片、文案、展示资源；
- 重新提审。

但如果是快速 4.3，重点还是先处理二进制相似度。大部分同源马甲包重复的是工程结构，不是 UI。

## 六、混淆

提审前的混淆必不可少，混淆参考如下：

![在这里插入图片描述](https://github.com/oyh6857451/app-store-review-guide/blob/main/images/boke1.png#pic_center)

| 功能 | 作用 |
|---|---|
| 垃圾代码注入 | 增加代码结构差异 |
| 字符串加密 | 降低字符串裸露 |
| 文件夹混淆 | 降低目录结构相似 |
| Model 混淆 | 降低数据层相似 |
| 随机类、随机参数 | 增加符号和编译差异 |
| 文件位置调换 | 打散工程结构 |
| 国际化混淆 | 处理多语言资源 |
| 资源混淆 | 处理资源名和资源目录 |
| 安全快照 | 支持回滚恢复 |

## 七、总结

4.3 常见原因就三类：

1. 二进制相似度高；
2. 元数据相似度高；
3. 账号和提交行为风险叠加。

解决重点也很明确：

1. 先处理 IPA 里的工程特征；
2. 再处理 App Store 页面元数据；
3. 控制提交节奏；
4. 为了稳定率，配合调整主题配色和数据源。
